# 诊断与实机测试

本文说明 Fn+D 诊断每个字段的含义和读法，并给出编号的实机测试项。发版规范按这些编号要求测试（见[发版规范](发版规范.md#6-实机验收)）。

## 1. 诊断输出

按 **Fn+D** 后松开所有键，键盘会逐字"打"出一行（约 30 ms 一个字符，一行要几秒）：

```
bridge75-via-v1.5-20261121-20261121-0356 fw=0 dev=1 state=2 wakes=3 source=1 retries=6 drops=0 sleep=0 bat=87 rx=1191 ack=352 valid=42 bad=0 tx=358 rgb=1/1/0 leds=7622 rail=0
```

输出规则：

- **开始条件**：所有键松开（包括 Fn）、没有修饰键，并且当前是 USB，或者无线已连接。不满足时一直等。
- **取样时刻**：开始输出的那一刻，不是按下的那一刻。
- **取消**：输出过程中切换设备会中止。
- **末尾没有回车**。Fn+B（`bat=NN`）和 Fn+D 共用一个输出缓冲，后按的会从头重新开始，两者不会交错。
- 计数从 MCU 上电开始累计。有电池，所以拔插 USB 不清零；刷机、断电、`_resetwake` 版每次唤醒都会清零。**两次输出相减才是那一段时间的数据。**

## 2. 字段

| 字段 | 含义 | 取值 / 读法 |
| --- | --- | --- |
| `bridge75-…` | 构建标识：`bridge75-<标签>-<YYYYMMDD-HHMM>` | 必须与文件名一致。`bridge75-dev` 表示没经构建脚本编译 |
| `fw` | 无线模块固件版本 | 一直是 0，是老问题（读不到版本），不影响使用 |
| `dev` | 当前设备 | 0 USB，1/2/3 蓝牙 1/2/3，6 为 2.4G |
| `state` | 无线连接状态 | 0 无，1 配对中，2 已连接，3 断开，4 被拒绝。USB 下无意义 |
| `wakes` | MCU 从休眠（STOP）唤醒的次数 | 只在真正睡下去又醒来时 +1 |
| `source` | 最近一次唤醒的原因 | 0 无，1 按键，2 模块消息（UART），3 线缆 |
| `retries` | ACK 超时重发的次数 | 见第 3 节 |
| `drops` | 丢弃的帧数 | 重试耗尽、队列满、串口半帧、报告缓存过期或溢出共用这一个计数，单看分不出来源 |
| `sleep` | 模块 30 分钟休眠开关（Fn+`） | 0 关（默认），1 开 |
| `bat` | 电量百分比 | 模块回报前是默认值 100 |
| `rx` | 从模块收到的字节数 | |
| `ack` | 确认了一帧的 ACK 数 | |
| `valid` / `bad` | 校验通过 / 失败的完整帧数 | `bad` 应为 0 |
| `tx` | 发给模块的帧数（含重发） | |
| `rgb=a/b/c` | 灯渲染器：开关 / 模式 / 挂起 | 正常为 `1/1/0` |
| `leds` | 灯回调次数 | 只要在增长就说明渲染在跑 |
| `rail` | 灯供电引脚（PB7）读值 | 0 表示供电打开（低有效）。不是电压测量 |

## 3. 读 UART 计数

模块发来的帧中，ACK 是固定的 3 字节 `61 0D 0A`，其余消息帧本项目也都是 3 字节（34 字节的 RAW 帧不用）。所以：

$$\text{收到的 ACK} = \frac{rx - 3 \times valid}{3}$$

由此算出：

| 算式 | 含义 | 正常值 |
| --- | --- | --- |
| `tx − 收到的 ACK` | 模块没回 ACK 的份数（丢包） | 很小，实测丢包率 0.14%–0.8% |
| `收到的 ACK − ack` | 作为"欠账"被抵掉的迟到 ACK | 只在有重发时出现，不应持续增长 |
| `ack + retries` | 应等于 `tx` | 相等 |
| `retries` | 每丢一份正好 +2 | 约为丢包数的 2 倍 |

判断：

- `retries` 远大于丢包数的 2 倍：出现了连锁重发（2227 构建出现过 `tx=20 retries=10 ack=10`，已修正）。
- `rx` 不增长：模块没供电或串口接收有问题。
- `rx` 增长但 `valid`/`ack` 不增长：协议、干扰或串口时序问题。
- `bad > 0`：线路干扰或帧错位，需要报告。
- `drops` 增长：要结合当时做了什么判断来源（见测试 T11）。

ACK 不带序号带来的取舍见[架构与设计](架构与设计.md#43-ack-对账)。

## 4. 读休眠计数

- 闲置后醒来，`wakes` 应比闲置前多，`source=1` 表示是按键叫醒的。
- `source=2` 很多：MCU 被模块消息反复唤醒，费电，需要报告。
- 闲置期间 `wakes` 没变：没进入休眠（插着线、有按键按住、有未发完的数据都会阻止休眠）。
- 首键是否正常要看**醒来后实际打出的字**，计数只能说明发生了几次唤醒。

## 5. 实机测试项

每项都按"操作 → 记录 → 通过标准"写。测试时把每一步的 Fn+D 原样记下来。

| 编号 | 项目 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| T1 | 刷入确认 | 刷机、退出 DFU、按 Fn+D | 前缀与文件名一致；输出末尾无回车 |
| T2 | 有线基本 | USB 下打字，快速连打、长按几个键后松开 | 无漏字、无卡键 |
| T3 | 设备切换 | Fn+1/2/3/4/5 依次切换并各打几个字；按住 Fn+1 一秒配对一次 | `dev` 依次为 1/2/3/6/0，连接后 `state=2`；配对时灯快闪 |
| T4 | 输出键 | USB 和蓝牙下各按一次 Fn+B，再按 Fn+D | 输出 `bat=NN`，与 Fn+D 的 `bat=` 一致；都没有回车 |
| T5 | 蓝牙闲置首键（核心） | 蓝牙 1 已连接、拔掉 USB、`sleep=0`。从最后一次按键开始分别闲置 **6 分钟**和 **35 分钟**，醒来先输入 `abcdef123456`（其中一轮用 Shift+A 开头），再按 Fn+D | 首字不丢、无明显延迟；`wakes` 增加、`source=1`、`state=2`、`bad=0` |
| T6 | 2.4G 闲置与主机睡眠 | 2.4G 下按 T5 闲置一轮；再让电脑睡眠后唤醒 | 首字不丢；电脑唤醒后无需操作即可打字 |
| T7 | 主机离开 | 蓝牙模式下关闭电脑蓝牙 30–60 分钟，再打开 | 10 秒内自动回连（按键可立即触发）；`source=2` 不应大量增长 |
| T8 | 待机耗电 | 闲置前后各记一次 `bat`，间隔数小时或整夜 | 记录下降幅度，用于版本之间对比 |
| T9 | 有线 VIA | 按[用户指南](用户指南.md#5-有线-via-改键)加载定义，改一个键、拔插确认保留；分配 DIAG/BAT/SLEEP 测试；切到蓝牙 | 能读写且保留；自定义键行为正确；无线下 VIA 列表里键盘消失 |
| T10 | 恢复默认 | 改过键位后按 Fn+Esc | 键图恢复默认，`dev=0`，`sleep=0` |
| T11 | 2.4G `drops` 来源 | 2.4G 保持连接，打一段字前后各按一次 Fn+D；再闲置一段时间前后各按一次 | 分别记录 `drops` 增长，判断来自打字还是闲置 |
| T12 | 模块休眠对照（可选） | `sleep=1` 下重复 T5 的 35 分钟 | 记录首键表现，与 `sleep=0` 对比 |

### 反馈格式

```
固件：bridge75_ansi_norgb_<标签>_<时间>.bin
测试：T5 蓝牙 35 分钟
闲置前：<Fn+D 输出>
醒来后输入：abcdef123456 → 实际出现：…
醒来后：<Fn+D 输出>
备注：主机系统、距离、是否插线等
```

同一种缺陷不一定每次都触发。一次通过不能证明没问题，一次失败也要结合多份日志和主机回归测试下结论。
