# 固件发版规范

规定一份固件从改代码到交给用户刷机要经过哪些步骤、产出哪些文件、怎么命名、怎么核对、什么条件下才算"已发布"。每次发版按本文逐项执行。

## 1. 术语

| 术语 | 含义 |
| --- | --- |
| 标签 | 描述一批改动的名字，由构建时的 `BRIDGE75_TAG` 指定 |
| 构建时间 | 构建脚本取的 `YYYYMMDD-HHMM`，写进文件名和固件 |
| 构建标识 | `<标签>-<构建时间>`，Fn+D 以 `bridge75-<构建标识>` 开头 |
| 开发构建 | 没经构建脚本编译，前缀 `bridge75-dev`，不得交给用户 |
| 候选版 | 通过第 4、5 节全部自动检查的构建 |
| 已发布 | 候选版通过第 6 节规定的实机测试 |

## 2. 版本命名

### 2.1 标签

格式 `via-v<版本号>-<YYYYMMDD>`，例如 `via-v1.5-20261121`。

- `<版本号>` 为 `<主>` 或 `<主>.<次>`（正则 `^via-v[0-9]+(\.[0-9]+)?-[0-9]{8}$`）。主版本号在**大的行为变化**（键位布局、协议、低功耗策略）时加 1；次版本号用于较小的用户可见改动或规范化的再发布。只修编译告警、文档、测试时可以不升版本。版本号由维护者决定。
- `<YYYYMMDD>` 是这一版开始构建的日期。
- 同一标签修正后重新构建时沿用标签，靠构建时间区分。
- `via` 前缀表示带有线 VIA 的这条线，不代表 VIA 官方的版本号。
- 历史标签 `final`、`ack`、`power`、`via`、`via2`、`diag3`、`v2` 不再使用。
- 不设 `BRIDGE75_TAG` 时脚本默认用 `final`，**发版时必须显式设置**。本地脚本不校验格式，只有 CI 校验。

### 2.2 产物文件名

以标签 `via-v1-20261121`、构建时间 `20261121-0246` 为例：

| 产物 | 文件名 |
| --- | --- |
| 正式版（软唤醒） | `bridge75_ansi_norgb_via-v1-20261121_20261121-0246.bin` |
| 回退版（复位唤醒） | `bridge75_ansi_norgb_via-v1-20261121_20261121-0246_resetwake.bin` |
| 校验值 | `SHA256SUMS-via-v1-20261121-20261121-0246` |
| 日志目录 | `logs-via-v1-20261121-20261121-0246/` |
| Fn+D 前缀 | `bridge75-via-v1-20261121-20261121-0246` |
| VIA 定义 | `docs/via/bridge75-norgb-via.json`（CI artifact 里叫 `bridge75-norgb-via.json`） |

日期出现两次是预期的：前一个是标签的一部分，后一个是构建时间。文件名里标签与时间之间是 `_`，前缀里是 `-`。

## 3. 构建前

逐项确认：

- [ ] 改动只在 `bridge75-qmk/` 里做；没有在 QMK checkout 里改过东西（会被同步覆盖）。
- [ ] 改协议、低功耗、报告队列时补了主机测试，并确认新测试在旧代码上会失败。
- [ ] 改自定义键位时，`info.json` 的 `keycodes`、`docs/via/bridge75-norgb-via.json` 的 `customKeycodes`、`.github/workflows/build.yml` 里的 `expected` 列表三处一致；没有加入没有处理函数的键位。
- [ ] 工作区干净（`git status` 为空），要构建的代码已经提交。这样构建才能对应到一个确定的提交。
- [ ] QMK checkout 在基线 `33292390974c75362ca30873c482d052e0bd7a63`（脚本不符时只警告不退出，要自己看）。

## 4. 构建

### 4.1 本地

```sh
cd bridge75-qmk
BRIDGE75_TAG=via-v<N>-<YYYYMMDD> ./build.sh
```

脚本依次执行，任一步失败即退出，不产出固件，日志保留在 `firmware/logs-<构建标识>/`：

1. 用 `rsync -c --delete` 把 `keyboards/shortcut/bridge75`、`keyboards/shortcut/wireless`、`tools/bridge75` 同步进 QMK checkout
2. `qmk lint`
3. 三组主机测试（无线协议、低功耗与 USB、板级启动）
4. 编译 `_resetwake` 版，再编译正式版
5. 生成 `SHA256SUMS-*`，把三个文件移入 `firmware/`

### 4.2 GitHub Actions

仓库 → **Actions** → **构建固件与 VIA 定义** → **Run workflow**，填标签。工作流只能手动触发，会校验标签格式，在固定 QMK 基线上跑同一套 lint、测试和编译，再额外核对 VIA 定义与第 5 节的检查项。产物在该次运行的 **Artifacts** 里，名为 `bridge75-<标签>-<运行号>`，保留 90 天。私有仓库的运行会计入账户的免费分钟数。

### 4.3 两种构建的差异

| 项 | 本地 | CI |
| --- | --- | --- |
| ARM GCC | Homebrew 8.5 | Ubuntu 22.04 自带 10.x（未锁定小版本） |
| QMK CLI | 1.2.0（`.venv-qmk`） | 1.2.0 |
| 构建时间时区 | 本机（UTC+8） | UTC |
| 标签格式校验 | 无 | 有 |
| VIA 定义一致性检查 | 无 | 有 |

两边编出的二进制**不会逐字节相同**。同一个版本只发布其中一边的产物，并在更新记录里写明来源。GCC 10 的告警更严（曾因 `-Wimplicit-fallthrough` 失败），本地通过不代表 CI 通过。

## 5. 构建后核对

在 `firmware/` 目录下执行，全部通过才算候选版：

```sh
cd firmware
B=<标签>-<构建时间>                         # 例如 via-v1-20261121-20261121-0246
shasum -a 256 -c SHA256SUMS-$B              # 两个文件都 OK
grep -ci warning logs-$B/build-*.log        # 每个都是 0
for f in bridge75_ansi_norgb_<标签>_<构建时间>*.bin; do strings "$f" | grep -o 'bridge75-[^ ]* fw'; done   # 两行都是 bridge75-$B fw
cat logs-$B/test-*.log                      # 三组测试都是 PASS
```

- [ ] 校验值 OK
- [ ] 编译告警为 0
- [ ] 两个 `.bin` 内嵌的前缀与文件名一致
- [ ] 三组主机测试通过，`lint.log` 无错误
- [ ] 改了键位时：用 CI 构建，或手工对照第 3 节的三处一致

## 6. 实机验收

测试项编号见[诊断与实机测试](诊断与实机测试.md#5-实机测试项)。

| 改动类型 | 发布前必须通过 |
| --- | --- |
| 任何发布 | T1、T2、T3、T4 |
| 改了无线协议、低功耗、重连 | 加 T5（6 分钟和 35 分钟各一轮）；涉及 2.4G 时加 T6 |
| 改了键位或 VIA | 加 T9、T10 |
| 改了电量或休眠策略 | 加 T7、T8 |

- 实测前在更新记录里标"候选版，待实机测试"，测完补上结果和对应的 Fn+D 输出。
- 只通过自动检查的构建可以交给用户测试，但必须明确说明是候选版，并给出回退文件。
- 实测失败时：更新记录里写明现象，不要删除或覆盖这份构建；修正后用新的构建时间重新构建。

## 7. 文档同步

每次构建出候选版后，同一次提交里更新：

1. **`docs/更新记录.md`** 顶部加一条，格式见下。上一条的状态改为"已被取代"，或补上实测结果。
2. **`README.md`** 的"当前状态"表。
3. **工作目录根下的 `README.md`**（给用户刷机的入口，不在 git 里）：指向新文件。
4. **`CLAUDE.md`** 的"当前状态"一节。

更新记录条目模板：

```markdown
## via-v<N>-<YYYYMMDD>（<构建时间> 构建，<状态>）

- 文件：`bridge75_ansi_norgb_<标签>_<构建时间>.bin`（回退版 `..._resetwake.bin`）
- 校验：`SHA256SUMS-<标签>-<构建时间>`；构建来源：本地 / CI 运行 #<号>
- 源码：提交 `<短哈希>`；基于 <上一版本>

**改动**
- 改了什么、为什么（用户能感知到的写在前面）

**验证**
- 自动：lint、三组主机测试、编译无告警；新增测试 `<名称>`（在旧代码上失败）
- 实机：<已通过的测试编号和结果，或"待测：T1–T4…">

**风险与回退**
- 可能的问题；出问题时刷回 <文件>
```

状态只用这几种：`候选版，待实机测试`、`已发布`、`已被 <版本> 取代`、`有缺陷，勿用`。

## 8. 提交与标记

1. 提交信息用中文，第一行概括改动，正文写原因和验证（命令、结果、构建标识）。
2. 推送 `main` 前先征得维护者同意。
3. **git 标签**：版本发布后，在构建所用的提交上打同名标签：

   ```sh
   git tag -a via-v<N>-<YYYYMMDD> <提交> -m "<构建标识>，<一句话说明>"
   git push origin via-v<N>-<YYYYMMDD>
   ```

4. **GitHub Release**（可选）：以该标签建 Release，附上两个 `.bin`、`SHA256SUMS-*` 和 VIA 定义，正文复制更新记录条目。`.bin` 不进 git，Release 是除本机 `firmware/` 和 90 天 CI artifact 外唯一的长期存档。

推送标签和建 Release 都是对外操作，需维护者确认后再做。

## 9. 产物管理

- `firmware/` 里的构建产物**只增不改**：不覆盖、不重命名用户实测过的文件；新构建一律带新的构建时间。
- 构建失败会留下没有对应 `.bin` 的日志目录（例如 `logs-via-20261121-0105`、`logs-via2-20261121-0154`），可以删除，删除前确认目录里没有 `build-soft.log`。
- 至少保留：当前版本、上一个已发布版本、diag3（唯一通过闲置首键实测的对照版）。
- diag3 和更早的产物没有构建时间、部分没有校验文件，引用时以文件名和内嵌前缀为准。

## 10. 回退

| 情况 | 刷回 |
| --- | --- |
| 新版本有功能回归 | 上一个已发布版本 |
| 正式版从休眠醒不过来 | 同一构建的 `_resetwake` 版（可能丢首键、计数清零） |
| 闲置首键问题复现 | diag3，用来对照 |

## 11. 已知缺口

以下问题目前靠流程弥补，后续可以改进：

| 缺口 | 现在的做法 | 可改进 |
| --- | --- | --- |
| 固件里没有提交哈希，只有标签和构建时间 | 构建前提交、更新记录写明提交、发布后打 git 标签 | 构建时把 `git rev-parse --short HEAD` 一并写进前缀 |
| 本地脚本不校验标签格式，默认 `final` | 人工按第 2 节设置 | 本地脚本也校验，不设标签时拒绝构建 |
| 本地与 CI 编译器版本不同 | 一个版本只发一边的产物 | 本地也用 GCC 10，或 CI 锁定版本 |
| `firmware/` 只在一台机器上 | 重要版本建 Release | |
